# AGENTS.md

Instructions for AI coding agents working in this repository. Humans stay accountable for every change: agents never merge, and a teammate approves every pull request. `CONTRIBUTING.md` has the full team rules.

## Project
PedalPoint: e-bike sharing for a university campus (fictional client Ria Nova University). Java 21, Spring Boot, PostgreSQL, Flyway. See [README.md](README.md).

## Layout
- `backend/` Spring Boot service (package `tqs.ua.pedalpoint.backend`, one sub-package per domain area, e.g. `hub`)
- `simulator/` Java 21 fleet simulator (package `tqs.ua.pedalpoint.simulator`): publishes telemetry over MQTT and charges docked e-bikes 1% per tick; `./mvnw -B verify` from `simulator/`
- `infra/` configuration of the containers (Mosquitto)
- `frontend/` not started yet
- `docs/` reports; `.github/` workflows and PR template

## Commands (run from `backend/`)
- Build, unit and integration tests: `./mvnw -B verify` (Docker must be running: integration tests use Testcontainers)
- Unit tests only: `./mvnw -B test`
- BDD: `verify` also runs the `.feature` files through `CucumberIT` (failsafe, Testcontainers); step definitions are in `tqs.ua.pedalpoint.backend.bdd`; report in `target/cucumber-reports/`.
- Run the stack: `docker compose up --build` (from the repository root)

## Code style
- Constructor injection; no field `@Autowired`.
- Schema is owned by Flyway (`src/main/resources/db/migration`, `V<n>__description.sql`); never rely on Hibernate DDL and never edit a migration already on `main`.
- Return DTOs (records) from controllers, never entities.
- Business rules live in services, not in controllers.
- Use external systems only through their interfaces (telemetry source, payment gateway); never call MQTT or Stripe from a service directly.
- Package names must match directories.

## Tests
- Unit tests (`*Test`): business logic, no Spring context, mocks for collaborators.
- Integration tests (`*IT`): run by failsafe in `verify`, real PostgreSQL via Testcontainers; pin image versions (no `latest`).
- Acceptance criteria of core stories become Gherkin scenarios (Cucumber): one `.feature` per story in `backend/src/test/resources/features`, tagged `@US-<n>`. Stories of the current iteration are listed in `docs/I2_user_stories.md`.
- A feature tagged `@wip` has no step definitions yet and is excluded from the run; remove the tag when the steps are implemented.
- A feature covers one story only: a scenario that tests the behaviour of another story goes in that story's feature.
- Every new business rule gets unit tests, including the error cases.
- Tests must be able to fail on a plausible bug; do not add tests that only restate the implementation.
- Never delete or weaken a failing test to make the build pass. Report it instead.

## Definition of done
1. The story's acceptance criteria are implemented and covered by tests.
2. `./mvnw -B verify` passes locally and CI is green, including the quality gate.
3. New endpoints are documented for OpenAPI.
4. The pull request lists what was generated by AI.

## Domain rules
- E-bike states: `AVAILABLE`, `CHARGING`, `RESERVED`, `IN_USE`, `MAINTENANCE`, `RETIRED` (`STOLEN` comes in I3).
- An e-bike at a hub below 20% battery is `CHARGING`: hidden from users, cannot be booked or unlocked. Docked e-bikes charge 1% per minute and go back to `AVAILABLE` at 20%.
- During a trip the e-bike stays `IN_USE` even below 20%; the trip is never stopped for low battery. It becomes `CHARGING` when the trip ends at a hub.
- The full business rules (R1–R25) and SLOs are in `docs/PedalPoint_Product_Specification.pdf`.
- A trip ends only with the e-bike locked at a hub with free space.
- Bookings are for a hub, a bike type and a period (start and end).
- Only `@ua.pt` email addresses can register.
- Limits (battery thresholds, durations, prices) come from configuration, never hard-coded.

## Workflow
- Work on one Jira story at a time. One branch per story, named with the Jira key: `PDP-<n>-short-description`; the key also goes in commit messages and the PR title.
- When a story has Gherkin acceptance criteria, use them as the specification.
- Keep changes limited to the story; do not refactor unrelated code.
- Open a pull request using `.github/pull_request_template.md`; CI must be green.
- Never commit secrets or personal data; use synthetic test data.
- Do not push or merge unless a human asked for it.
